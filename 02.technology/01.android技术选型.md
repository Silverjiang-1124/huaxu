# Android Demo 技术选型

日期：2026-10-31｜状态：Demo 阶段建议，实施前验证构建组合｜依据：首次访谈分析及 Android 官方文档

## 决定

采用 **Kotlin + Jetpack Compose 的 Android 原生单机应用**，以本地数据验证日单量、工作负荷和轻量录入；不设服务器或账号。客户希望减少回复耗时及自动统计，但自动化方式仍需单独验证。选型是为快速制作可在 Android 手机上试用的 Demo，不代表产品功能和交互已经确认。

| 层面 | 选型 | 原因与边界 |
| --- | --- | --- |
| 平台与语言 | Android 原生、Kotlin | 现阶段只明确 Android；直接使用系统能力，便于真机验证，暂不为未知 iOS 需求承担跨平台复杂度。 |
| UI | Jetpack Compose + Material 3 | 适合快速迭代移动端界面；可自定义视觉，不必使用默认模板外观。 |
| 状态与业务 | 单 Activity；Compose + ViewModel + StateFlow；Kotlin 协程；小型 repository | 按界面层、数据层分离，保留简单的数据访问边界；单模块即可，暂不引入复杂分层、依赖注入框架或多模块。 |
| 业务数据 | Room（SQLite） | 支持按日期查询、更新与统计，适合后续逐步增加数据字段；使用数据库迁移保护已有试用数据。 |
| 简单设置 | DataStore | 用于每日容量等小型偏好；不用于保存订单明细。若首版设置很少，也可先放数据库，避免无谓依赖。 |
| 导出与恢复 | JSON，Android 系统文件选择器（Storage Access Framework） | 用户主动选择文件位置；如使用真实数据，需实现导出、导入校验和恢复测试。数据可能包含客户信息，应说明文件保管责任。 |
| 提醒 | 首版优先页面内展示，不默认请求通知权限 | 是否需要提醒尚未确定；需要时再评估 WorkManager 或系统通知。WorkManager 为延迟容忍型工作，不保证准点；精确时间另受系统权限约束，须真机验证。 |
| 构建 | Gradle Wrapper + Gradle Kotlin DSL，JDK 17 | 可复现构建；具体依赖版本在创建工程并验证兼容性后固定并提交。 |
| 验证 | JUnit；Room 查询/迁移测试及真机冒烟测试 | 优先覆盖容量计算、日期边界、导出恢复等有业务后果的逻辑，不为界面样式堆砌测试。 |

Android 官方建议使用 Compose、ViewModel、分层数据访问和单向数据流；Room 适合本地结构化数据。[架构建议](https://developer.android.com/topic/architecture/recommendations) · [Room](https://developer.android.com/training/data-storage/room) · [DataStore](https://developer.android.com/topic/libraries/architecture/datastore/)

## 版本与构建基线

- 暂定最低 Android 8.0（API 26）；这只是开发起点，必须先核对种子客户的手机系统版本。若客户设备更旧，调整最低版本并实测。
- 建议首轮采用 Android Gradle Plugin 9.2.0、Gradle 9.4.1、JDK 17 的官方兼容组合，`compileSdk` 和 `targetSdk` 暂定 API 36；现有启动页已使用 Compose BOM 2026.03.00 与 Kotlin Compose 插件 2.2.10 构建成功；Room/KSP 尚未引入，届时需再验证。[AGP 9.2 兼容性](https://developer.android.com/build/releases/agp-9-2-0-release-notes) · [Compose 配置](https://developer.android.com/develop/ui/compose/setup-compose-dependencies-and-compiler)
- 生成并提交 Gradle Wrapper；SDK 本身、`local.properties`、构建产物和签名密钥不入库。真实客户资料及录音转写也不应上传到公开远程仓库，分享前需审查当前 Git 历史。
- Debug APK 用于内部验证；试用分发前核对设备安装限制、安装来源提示和签名/升级策略。无应用商店发布承诺。

## 方案对比

| 方案 | 优点 | 当前取舍 |
| --- | --- | --- |
| Kotlin + Compose | 原生 Android 能力完整、单平台依赖少，适合面向种子客户迭代 | 选用；未来 iOS 需另做客户端或重新评估共享策略。 |
| Flutter | 将来多平台可复用大部分 UI 和业务 | 本阶段只有 Android 的确定需求；需引入 Flutter/Dart 工具链，暂不选。 |
| Web/H5 或套壳 | 页面原型快，跨平台访问方便 | 做需求演示可用；但当前目标是独立 Android 应用并需验证手机本地数据和系统交互，暂不作为交付架构。 |

## Demo 待验证范围

1. 用虚构样本快速记录某天的张数和工作量类型，允许改错、删除；验证可接受的录入时间。每日容量由用户设置，不把访谈中的十张写死成业务规则。
2. 查看当天及未来几天的计划量和剩余容量；数量、工作量、接单日期、交付日期等概念须与客户确认。
3. 用少量可复制的话术作为回复辅助候选；它不能代替自动回复，也需要客户验证是否节省时间。
4. 验证关闭重开后数据仍在；使用真实订单试用前实现和验证导出/恢复。

以上是试验范围建议而非承诺的最终功能，先做交互和真实业务验证，记录每项结论。只统计每日数量无法确定某个客户是否漏单；提醒也不能发现从未录入的数据。

## 自动化和隐私边界

- 不假定能读取微信或 QQ 的完整聊天、付款记录，或能在个人微信自动发送消息；需逐项核实官方接口、使用权限、平台政策及真机表现。通知读取只能处理系统实际提供并经用户授权可见的通知，可能缺失或变化，不应视为完整账单或自动记单依据。
- 不依赖无障碍模拟点击、抓取私人聊天或绕过平台限制作为 Demo 默认方案。先对比手动快速录入、系统分享或明确授权的官方能力。
- 本地存储不等于可靠备份；卸载、清除数据、设备损坏或换机会造成丢失。系统自动备份受设备和配置影响，不能代替验证过的用户可操作导出与恢复。
- 提醒如需精确时间，Android 对精确闹钟有额外限制；通知权限、系统省电与各厂商行为需实际测试。[定时任务与精确闹钟](https://developer.android.com/develop/background-work/services/alarms) · [文档与文件访问](https://developer.android.com/training/data-storage/shared/documents-files)
