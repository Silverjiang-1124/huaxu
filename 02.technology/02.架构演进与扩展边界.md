# 从单机 Demo 到联网产品：架构演进记录

日期：2026-10-31｜状态：设计约束与演进方向，尚非服务端选型或已实现功能

## 目标与原则

用户明确要求为未来的账号鉴权、商业化、服务端和数据库预留扩展能力。首个 Demo 仍以验证画师的使用体验为目标；但业务逻辑、界面、存储和未来网络能力需要有明确边界，避免将本地数据库或单一用户假设散落在界面代码中。

## 客户端结构

```text
界面（Compose）
    ↓ 状态和用户操作
ViewModel / 业务计算
    ↓ 业务接口
Repository 接口
    ↓ 当前                  ↓ 未来按需求增加
本地数据源 Room          网络数据源 / 鉴权会话
```

- 先保持单个 Android 工程模块，按 `ui`、`domain`、`data` 等包组织；当代码规模确实需要时再拆模块。界面不直接读写 Room、调用网络或判断付费状态。
- Repository 暴露业务需要的操作和数据，不把 Room Entity、SQL 或未来 HTTP 响应直接传到界面。业务规则和日期、工作量计算集中维护，可独立测试；DTO、数据库实体与业务模型通过映射转换。
- 提供统一的依赖组装入口，Demo 可手动构造依赖；未来加入网络、鉴权或测试替身时可替换实现，不提前强制引入复杂依赖注入框架。
- 区分计划日期、创建时间、完成时间和数量等含义；日历日期按业务日期保存，跨时区时间点以 UTC 表达，显示时转换。容量、订单与每日汇总的真实关系需先向画师确认，避免现在把“每日数量”强行建成完整订单系统。

## 本地数据和未来同步

- 数据库使用稳定的客户端生成 UUID 作为记录标识，不使用昵称、日期或自增序号作为跨设备身份。保留创建、更新时间及必要的数据版本；日期和状态等字段语义应明确。字段以实际业务为准，不把未经确认的设计当作现成协议。
- Room 保持 schema 版本和迁移路径；导出格式带版本号，导入先校验再以事务方式写入，明确覆盖或合并行为，避免误覆盖。使用真实数据前，测试导出、恢复及升级迁移。
- Demo 可以只有本地数据源。后续增加云端时，repository 内部再协调本地和服务端；**接口分离只能降低改造范围，不能自动解决同步、鉴权或数据迁移**。
- 真正实现离线编辑或多设备同步前，需要单独设计并验证：本地数据绑定哪个账户、未登录记录如何认领、登录切换/退出后的数据隔离、客户端写入失败重试和幂等、版本冲突、删除与恢复、时钟误差及服务器裁决。无需在 Demo 中假装已有同步保障。
- 未来服务端应独立校验归属及授权，用户 ID 应由已验证的服务端会话确定，不信任客户端提交的账号或租户标识。服务端数据库模型、备份恢复和权限隔离在后端方案确定时设计。

## 鉴权与商业化边界

- Demo 阶段不实现登录、账号绑定或支付，但业务存储和界面避免写死“永远只有一台设备或一个用户”。未来视实际需求选认证方式、会话管理和授权模型。
- 后续接入身份验证时，只通过 HTTPS 调用服务端；令牌存储、刷新、失效、登出及设备丢失场景单独设计。Android 密钥材料可使用系统 Keystore 保护；不把密钥或服务端密钥写入 App、仓库或导出文件。真正上线前应做端到端安全审查。
- 后续若有收费，客户端展示权益，服务端依据可信购买或订阅记录计算并校验权益，核心受限操作由服务端执行授权；不能以客户端布尔值作为防护。支付渠道、计费方式、订阅生命周期和离线体验尚未决定。
- 云服务和商业化上线前需补充用户数据处理、隐私授权、账号注销、数据导出及删除、备份策略等产品和合规设计；当前不假定具体法规或平台接入方案。

## 分阶段实施

| 阶段 | 实际交付 | 关键验收 |
| --- | --- | --- |
| Demo | 单机 UI、业务逻辑、Room 数据源、必要的导出与恢复 | 主流程可用、重启不丢数据、真实试用前备份恢复验证、核心计算与迁移测试。 |
| 联网验证 | 根据需要新增 API 客户端、后端与鉴权，明确本地数据的账户归属 | 登录/退出和切换账户、旧数据认领、权限隔离、网络异常及恢复均经测试。 |
| 产品化 | 依据商业方案补充账号生命周期、权益、运维、备份和监控 | 服务端授权、购买状态一致性、数据恢复、隐私与安全流程得到验证。 |

服务端语言、框架、数据库、API 协议、部署和支付渠道暂不选型；等真实联网场景、成本和团队条件明确后再比较。当前不产生服务端实施承诺。
